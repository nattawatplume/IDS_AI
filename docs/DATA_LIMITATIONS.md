# ข้อจำกัดของข้อมูล

ทุกตัวเลขของโครงงานนี้ต้องอ่านคู่กับเอกสารนี้ (ขยายจากหัวข้อ 1 ของ spec)

## 1. ข้อมูลที่มีจริง

| ข้อจำกัด | ผลต่อการออกแบบและการอ่านผล |
|---|---|
| คลังข้อมูลย้อนหลังของ Binance spot (data.binance.vision) มีแค่ trades, aggTrades และ klines ไม่มีสมุดคำสั่ง (order book) ย้อนหลัง | การตรวจ spoofing, layering และ quote stuffing ต้องใช้ข้อมูลที่บันทึกเองหรือข้อมูลสังเคราะห์ MVP ตรวจจากการซื้อขาย (Track T) เท่านั้น |
| ทีมบันทึกข้อมูลสดได้ครั้งละไม่กี่ชั่วโมง | ข้อมูลสดใช้ตรวจความสมเหตุสมผลและการเตือนผิด ไม่ใช่วัด recall |
| ข้อมูลสาธารณะไม่มีรหัสบัญชีของผู้ซื้อขาย | wash trading พิสูจน์ไม่ได้ ทำได้แค่ "รูปแบบที่คล้าย wash" |
| ป้ายเหตุการณ์ปั่นราคาจริงมาจากประกาศใน Telegram (เวลาประกาศ และไม่ครบทุกเหตุการณ์) | การเตือนนับว่าตรงกับเหตุการณ์ถ้าทับช่วง [เวลาในป้าย − 2 นาที, เวลาในป้าย + 5 นาที] วันที่ไม่มีป้ายอาจมีการปั่นที่ไม่มีใครบันทึก การเตือนผิดที่วัดได้จึงอาจสูงเกินจริง |
| ป้ายจริงเป็นคู่เหรียญกับ BTC ช่วงปี 2018–2022 เท่านั้น | ผลบนข้อมูลจริงใช้ได้กับคู่ BTC ช่วงนั้น ห้ามอ้างว่าใช้กับคู่ USDT ปัจจุบันได้ |
| คู่ BTC ขนาดเล็กซื้อขายห่างๆ และราคาขยับทีละขั้น (tick) ที่ใหญ่ | ระบบมีค่าต่ำสุดของสเกลตามขนาด tick เพื่อไม่ให้ค่า z พุ่งจากการขยับราคาเพียงขั้นเดียว แต่ความไวยังต่างจากคู่ที่ซื้อขายถี่ |
| วันที่ไม่มีในคลังข้อมูล หรือไม่มีวันก่อนหน้า | วันนั้นถูกข้ามพร้อมบันทึกเหตุผล (`missing_day`, `no_baseline`) เพราะระบบต้องเทียบกับ 24 ชั่วโมงก่อนหน้าเสมอ |
| เวลาของข้อมูลสดมาจากนาฬิกาของ Binance และเครื่องรับ | ระบบชดเชยนาฬิกาเครื่องที่คลาด แต่ช่วงที่เน็ตหลุดนานไม่มีข้อมูล ระบบเริ่มนับหน้าต่างใหม่และไม่เดาข้อมูลที่หายไป |

## 2. ผลการตรวจเวลาในป้าย (label alignment)

ก่อนเชื่อตัวเลข REAL ใดๆ ต้องตรวจว่าเวลาในป้ายตรงกับช่วงที่มีการซื้อขายมากที่สุดจริง ด้วย `uv run idsai labels --align`

> **ยังไม่ได้วัดกับข้อมูลจริง** ผลจะเติมในขั้นรันข้อมูลจริง (Task 20): จำนวนป้ายที่วัดได้, ฮิสโทแกรมของ lag, ค่ามัธยฐานของ |lag| และค่า `label_offset_s` ที่ใช้

ถ้าค่ามัธยฐานของ |lag| ตั้งแต่ 120 วินาทีขึ้นไป หรือวัดไม่ได้เลย คำสั่งจะจบด้วยรหัส 1 และห้ามรายงานตัวเลข REAL จนกว่าจะแก้ `label_offset_s` ใน `configs/splits.yaml` แล้วตรวจผ่าน

## 3. ข้อจำกัดของวิธีวัดผล

- ป้ายจริงมีไม่กี่ร้อยเหตุการณ์ ช่วงความเชื่อมั่น (CI) จึงกว้าง รายงานแสดง CI ทุกครั้ง
- เมื่อ recall เป็น 0 หรือ 1 CI แบบ bootstrap จะหดเหลือจุดเดียว รายงานจึงเพิ่มขอบเขตแบบ "rule of three" (3/n)
- precision แสดงคู่กับสัดส่วนแถวที่เป็นเหตุการณ์ (prevalence) เสมอ เพราะ precision ขึ้นกับว่าเหตุการณ์หายากแค่ไหน
- ผล SEMI-SYN มาจากการใส่เหตุการณ์จำลองลงในวันปกติจริง จึงบอกได้แค่ว่าระบบจับรูปแบบที่เราจำลองได้แค่ไหน ไม่ได้บอกว่าจับการปั่นจริงได้แค่ไหน
- เกณฑ์การเตือน (alert budget) ตั้งจากช่วงปกติที่ใช้สอบเทียบ ถ้าตลาดเปลี่ยนไปมาก อัตราการเตือนจริงจะคลาดจากงบ ตัวตรวจสุขภาพ (Auditor) เฝ้าดูเรื่องนี้

## 4. สิ่งที่เราไม่อ้าง

- เราไม่อ้างว่าการเตือนคือหลักฐานว่ามีการปั่นราคา หรือว่าใครเป็นผู้ทำ
- เราไม่อ้างว่า anomaly p-value คือความน่าจะเป็นที่มีการปั่นราคา มันบอกแค่ว่าช่วงนั้นหายากแค่ไหนเมื่อเทียบกับช่วงปกติ
- เราไม่อ้างว่าผลบนคู่ BTC ปี 2018–2022 ใช้ได้กับคู่ USDT หรือช่วงเวลาปัจจุบัน
- เราไม่อ้างว่าระบบจับ spoofing, layering หรือ quote stuffing ได้จากข้อมูลจริง
- เราไม่อ้างว่าวันที่ไม่มีป้ายคือวันที่ไม่มีการปั่นราคา
- เราไม่อ้างความแม่นยำโดยรวมเป็นตัวเลขเดียว และไม่ใช้ accuracy
- เราไม่อ้างว่า AI ดีกว่าวิธีพื้นฐาน เว้นแต่ผลต่างผ่านเกณฑ์ (ขอบล่างของ 95% CI แบบ paired bootstrap มากกว่า 0 และผลต่างอย่างน้อย 0.02)
- ชุดเดโม (`demo-pack`) มีแค่ไม่กี่วัน ใช้สาธิตการทำงาน ไม่ใช้วัดผล
