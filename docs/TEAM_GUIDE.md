# คู่มือทีม

## 1. ใครดูแลส่วนไหน

| บทบาท | ดูแล | งานหลัก |
|---|---|---|
| Role 1: ข้อมูล | `idsai/data/`, `idsai/bus.py`, CI (`.github/workflows/ci.yml`) | โหลดและตรวจไฟล์ย้อนหลัง, รับข้อมูลสด, เก็บข้อมูล, เล่นซ้ำ |
| Role 2: ตรวจจับ | `idsai/detection/` | ตัวเลขสรุป (features), กฎ, สถิติ, Red-Team simulator, taxonomy |
| Role 3: AI และการวัดผล | `idsai/ai/`, `idsai/eval/` | autoencoder, วิธีพื้นฐาน, Chief, การฝึกโมเดล, การทดลองและรายงาน |
| Role 4: ผลิตภัณฑ์และเอกสาร | `idsai/product/`, `docs/`, `README.md`, `NOTICE.md` | API, Dashboard, คำอธิบายภาษาไทย, เอกสาร |

`idsai/cli.py` และ `idsai/contracts/` เป็นของกลาง แก้แล้วต้องบอกทุกคน เพราะทุกส่วนพึ่งรูปแบบข้อมูลเหล่านี้

## 2. เพิ่มตัวตรวจจับใหม่ใน 3 ขั้น

1. **เขียน class** ที่สืบทอด `Detector` (`idsai/contracts/detector.py`) กำหนด `name`, `layer` (`rule`, `stat`, `ai` หรือ `baseline`), `technique_ids`, `requires` (คอลัมน์ feature ที่ใช้) แล้วเขียน `score` (คืนคะแนนหนึ่งค่าต่อแถว ยิ่งสูงยิ่งผิดปกติ และคืน NaN ถ้า feature ที่ต้องใช้เป็น NaN) กับ `evidence` (feature ที่มีส่วนมากที่สุดไม่เกิน 5 ตัว) ถ้าต้องฝึก ให้เขียน `fit`, `state_dict` และ `load_state_dict` ด้วย
2. **ลงทะเบียน** ใน `idsai/detection/registry.py` ด้วย `register("stat.my_detector", factory)` โดย factory รับ `(cfg, seed)` แล้วคืนตัวตรวจจับ
3. **เปิดใช้** โดยใส่ชื่อในรายการ `detectors:` ของ `configs/default.yaml` แล้วเขียนชุดทดสอบใน `tests/detection/` หรือ `tests/ai/`

ไม่ต้องแก้ Chief, API หรือหน้าจอ Chief แปลงคะแนนทุกตัวเป็น anomaly p-value เอง ข้อควรระวัง:

- ตัวตรวจจับใน `idsai/detection/` และ `idsai/ai/` ห้าม import `idsai.eval`, `idsai.data`, `idsai.pipeline` หรือ `idsai.ai.learning` (กันการแอบดูป้ายเฉลย) ชุดทดสอบ `tests/test_leakage_guard.py` ตรวจให้
- ห้ามใช้ feature ที่บอกเวลาในวัน (ชั่วโมง นาที)
- ถ้าตัวตรวจจับใหม่มีสถานะต่อแถว (จำค่าระหว่างการเรียก `score`) ผลของ stream กับ batch จะไม่ตรงกัน ให้ย้ายสถานะไปไว้ใน feature kernel แทน

## 3. ชุดทดสอบ

```bash
uv run pytest                                   # ทั้งหมดยกเว้นที่ต้องใช้เน็ต (ใช้เวลาหลายนาที)
uv run pytest -q -m "not network and not slow"  # เหมือน CI
uv run pytest tests/test_cli.py                 # เฉพาะไฟล์
uv run ruff check .                             # ตรวจรูปแบบโค้ด
```

- ชุดทดสอบไม่ใช้เน็ต ข้อมูลทดสอบสร้างจาก `tests/synth.py` การดาวน์โหลดใน `tests/test_cli.py` ใช้ตัวโหลดปลอม
- เครื่องหมาย `slow` ใช้กับทดสอบที่ขึ้นกับความเร็วเครื่อง (CI ข้าม) ส่วน `network` ใช้กับทดสอบที่ต้องต่อเน็ตจริง (ปกติข้าม)
- CI รันบน Ubuntu และ Windows ด้วย Python 3.13: `uv sync --frozen`, `uv run ruff check .`, `uv run pytest -q -m "not network and not slow"`

## 4. เรื่องที่ต้องรู้ก่อนรันจริง

- **Windows กับ path ยาว:** Windows จำกัด path ไว้ราว 260 ตัวอักษร ข้อมูลอยู่ลึก เช่น `data/trades/symbol=.../date=.../part.parquet` และ `data/features/...` ให้เก็บโปรเจกต์ในโฟลเดอร์สั้นๆ เช่น `C:\IdsAI` และไม่ส่ง `--basetemp` ยาวๆ ให้ pytest
- **แก้ช่วง train ใน `configs/splits.yaml`:** ต้องแก้หรือลบ `drift_v1` และ `drift_v2` ด้วย เพราะสองช่วงนี้ต้องอยู่ภายในช่วง train (ถ้าลบ ระบบใช้ 2 ใน 3 แรกและ 2 ใน 3 หลังของช่วง train ให้เอง) ไม่อย่างนั้นการอ่านค่าตั้งจะล้ม
- **เปลี่ยนค่าตั้งแล้วต้อง train ใหม่:** ชุดโมเดลจำ `config_hash` ไว้ ถ้าค่าตั้งเปลี่ยน `serve` จะไม่ยอมโหลด
- **โหมดสด:** รัน `download --symbols ... --days 8` แล้ว `train --profile live` ก่อน `serve --mode live` จะโหลดข้อมูลย้อนหลัง 2 วันล่าสุดที่เผยแพร่แล้วมาอุ่นเครื่อง แถวแรกมาราว 30 นาทีหลังเชื่อมต่อ ถ้าข้อมูลย้อนหลังจบไปนานเกิน 17.5 ชั่วโมง ค่าเทียบกับช่วงปกติจะใช้ได้หลังราว 6.6 ชั่วโมง (ระบบพิมพ์ลำดับเวลานี้ทุกครั้งที่เริ่ม)
- **API ไม่มีล็อกอิน:** `serve` เปิดที่ `127.0.0.1` เป็นค่าเริ่มต้น และรับเฉพาะคำขอที่ระบุชื่อเครื่องในรายการที่อนุญาต ถ้าต้องการให้เครื่องอื่นเข้าได้ ให้ใช้ `--host <IP ของเครื่องนี้>` แล้วเรียกด้วย IP นั้น (`--host 0.0.0.0` เปิดรับทุกเครือข่าย แต่ API จะรับเฉพาะคำขอที่เรียกด้วย `127.0.0.1` หรือ `localhost`)
- **ความเร็วการเล่นซ้ำ:** `--speed 0` คือเร็วสุด แต่ API จะตอบช้าลง (ค่ามัธยฐานราว 140 มิลลิวินาที) ค่าเริ่มต้นคือ 60 เท่า

## 5. คำศัพท์

| คำ | ความหมาย |
|---|---|
| symbol-day | ข้อมูลของเหรียญหนึ่งในหนึ่งวัน (UTC) หน่วยพื้นฐานของการแบ่งข้อมูลและการนับการเตือน |
| D-1 | วันก่อนหน้า ต้องมีเสมอ เพราะทุกค่าเทียบกับ 24 ชั่วโมงก่อนหน้า |
| window / หน้าต่าง | ช่วงเวลาที่สรุปเป็นตัวเลข (10, 60, 300, 1800 วินาที) คำนวณใหม่ทุก 10 วินาที |
| baseline | ค่าปกติของเหรียญจาก 24 ชั่วโมงก่อนหน้า ใช้ได้เมื่อมีตัวอย่างอย่างน้อย 6 ชั่วโมง |
| robust z | ค่าปัจจุบันห่างจากค่ากลางของ baseline กี่เท่าของความกระจาย (ทนต่อค่าสุดโต่ง) |
| detector / ตัวตรวจจับ | ส่วนที่ให้คะแนนความผิดปกติต่อแถว แบ่งเป็นชั้นกฎ สถิติ และ AI |
| Chief | ส่วนที่รวมคะแนนทุกชั้น แปลงเป็น anomaly p-value แล้วตัดสินว่าจะเตือนไหม |
| anomaly p-value | ความหายากเทียบตลาดปกติ ยิ่งน้อยยิ่งหายาก ไม่ใช่ความน่าจะเป็นที่มีการปั่นราคา |
| alert budget | จำนวนการเตือนที่ยอมรับได้ต่อสัญลักษณ์-วันบนข้อมูลปกติ ใช้ตั้งเกณฑ์ (tau) |
| tau | เกณฑ์ของคะแนนรวม แถวที่ถึงเกณฑ์ติดกันรวมเป็นการเตือนหนึ่งครั้ง (episode) |
| calibration / สอบเทียบ | เก็บคะแนนบนวันปกติที่ไม่ได้ใช้ฝึก เพื่อแปลงคะแนนเป็น p-value และตั้ง tau |
| label / ป้าย | บันทึกเวลาของเหตุการณ์ปั่นราคาจริงจาก Telegram (Sapienza, Hu et al.) |
| label alignment | การตรวจว่าเวลาในป้ายตรงกับช่วงที่ซื้อขายมากที่สุดจริง (`labels --align`) |
| recall | สัดส่วนเหตุการณ์ที่ระบบเตือนทัน |
| false alert / การเตือนผิด | การเตือนที่ไม่ตรงกับป้ายใด นับต่อสัญลักษณ์-วัน |
| provenance | ที่มาของตัวเลข: REAL (ป้ายจริง), SEMI-SYN (ใส่เหตุการณ์จำลองลงข้อมูลจริง), SYN (สังเคราะห์ทั้งหมด) |
| bundle / ชุดโมเดล | โฟลเดอร์ที่มีโมเดลที่ฝึกแล้ว สถานะของ Chief และ `bundle.json` ที่ `serve` โหลด |
| demo pack | ชุดข้อมูลและโมเดลเล็กใน `data/demo/` สำหรับสาธิต |
| replay / live / sim | เล่นข้อมูลเก่าซ้ำ / ข้อมูลสด / ข้อมูลจำลอง |
| Red-Team | การใส่เหตุการณ์ปั่นราคาจำลองเพื่อทดสอบระบบ ทำได้เฉพาะ replay และ sim |
