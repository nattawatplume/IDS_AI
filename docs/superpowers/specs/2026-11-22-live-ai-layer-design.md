# Live AI layer: ship the M2 pick (`iforest:shift1`)

Source: `docs/REPORT.md` §11 (M2). Branch `feat/live-ai` (worktree `IdsAI-live`), cut from `feat/m2` (0454009).

**Why.** M2's accept-only rule picked `iforest:shift1`: IsolationForest as the AI layer, its contribution to F is `max(0, −log10 p − 1)`. On test it lifts REAL recall_any from 0.745 to 0.785 (+0.040, significant) at the same hard-day FA (5.55). The user approved following the plan, so the live and replay systems should run this AI layer.

**Gap today.** The fusion mode exists only inside the eval (`AiFusion` passed by `experiments.py`). `ChiefCfg` has no field for it, so every production Chief (live bundle, replay, demo pack) uses the default `"fuse"`, and `configs/default.yaml` lists `ai.autoencoder_trade` as the AI detector.

## Changes
1. **`ChiefCfg`** (`idsai/config.py`) gets the fusion settings, mirroring `AiFusion`:
   - `ai_mode: Literal["fuse", "exclude", "mondrian", "shift"] = "fuse"`
   - `ai_shift: float = 0.0`
   - `ai_regime_feature: str | None = None`
   - Use the same validation rules `AiFusion` enforces. Reuse its checks rather than copying them.
   - **Hash safety:** when all three are at their defaults, they are absent from every dump, the same trick as `FeatureCfg.sell_side`. So `config_hash` of every existing config (including `configs/eval_prev_live.yaml` = `53e3b662ab96`) stays byte-identical. Add a test.
2. **Every production Chief honours it.**
   - Find every place outside the eval that builds a `Chief` or `ChiefStream`: bundle training and `load_bundle` in `idsai/ai/learning.py`, live-prep, replay pipeline, demo pack, and anything else grep finds. Each must pass `AiFusion` built from `cfg.chief`.
   - `load_bundle` must refuse a bundle whose stored Chief fusion differs from the config. The stored state already carries `AiFusion`, and the bundle's `config_hash` already covers it once the field is dumped. Make sure the error message is in Thai, like the others.
   - The eval keeps passing its own `AiFusion` per variant. Do not change eval results. Existing eval tests and golden/parity tests must pass unchanged.
3. **`configs/default.yaml`:**
   - `detectors: [rules, stat.robust_z, stat.cusum, ai.iforest]`
   - `chief: ai_mode: shift`, `ai_shift: 1.0`
   - Leave `configs/eval_prev_live.yaml` alone.
   - Check whether other configs used by deploy (`Dockerfile`, `start.sh`, `render.yaml`, any `configs/live*.yaml`) need the same change. Keep them consistent with default.
4. **Product / UI / Telegram / auditor:**
   - grep for hard-coded `autoencoder_trade`, `"AE"`, `ai.autoencoder`, and similar. Any place that assumes the AI detector is the AE must work with `ai.iforest`. Examples: evidence labels, Thai text such as "AE", health checks in `idsai/ai/auditor.py`, live-check, demo pack.
   - Show the AI detector with a neutral Thai label, e.g. "ชั้น AI (IsolationForest)". Never call F or p a probability. Never accuse anyone.
   - If the AE is no longer listed, the live bundle build must not train it, so there is no torch training at Docker build. Check the build path (`idsai live-prep`, Dockerfile) and the memory note: Render has 512 MB. IsolationForest with 200 trees on 256-row subsamples is small, but confirm that scoring all rows does not add a large peak (no full-matrix copies beyond what the AE path did).
5. **Docs:**
   - `docs/REPORT.md` gets a short note under §11 that live/replay now run `iforest:shift1`, with the commit.
   - `README` / deploy docs only if they name the AE as the live AI layer.

## Results / deviations

Built on `feat/live-ai` (not pushed).

- **`ChiefCfg.ai_mode / ai_shift / ai_regime_feature`.** The validation moved into one function, `idsai.config.check_ai_fusion`, called by both `AiFusion.__post_init__` and a `ChiefCfg` model validator (`config` cannot import `chief`, which already imports `config`). `AiMode` and `AI_MODES` moved to `config` with it. `AiFusion.from_cfg(cfg.chief)` builds the production fusion. The serializer drops the three keys only when all three are at their defaults. `eval_prev_live.yaml` still hashes to `53e3b662ab96`, and the pre-change `default.yaml` still hashes to `6da45ffe7efd`.
- **Production Chief sites.** There are only two: `fit_and_calibrate` (`idsai/eval/experiments.py`), which `train_and_save` uses for `train --profile research|live` and `demo-pack`, and `load_bundle` (`idsai/ai/learning.py`), which `serve` (replay and live) and `scripts/bench_latency.py` use. `StreamPipeline` wraps the Chief it is given in a `ChiefStream`, so it needs no change. The experiments still pass their own `AiFusion` (`run_detectors(..., ai=...)`). Note that `fit_and_calibrate` is called only by the CLI. `load_bundle` checks the stored Chief fusion before `Chief.load_state_dict` and refuses a mismatch in Thai. A different `ai_mode` in the config is already caught by `config_hash`; the new check catches a state that was edited while the hash still matches.
- **Bug found and fixed (two steps):** a bundle holding `ai.iforest` could never load. A fitted sklearn model does not pickle to the same bytes after a load, nor in another process, so the sha check failed with "โมเดล ai.iforest v1 ... ไม่ตรงกับที่บันทึกไว้". The first fix (re-pickle once before hashing) worked only within one process; review found that `serve` still refused a bundle built by `train`/`demo-pack` in another process. Now `bundle.json` stores the sha of the exact `state.pkl` bytes in the registry, and `load_bundle` checks the raw bytes (`ModelRegistry.load_raw`) before unpickling. For the AE those bytes are what `pickle.dumps` gave, so the shas of existing AE and demo-pack bundles stay valid (a test pins this). Tests save a default-config bundle in one subprocess and load it in another, and a value changed in the stored model is still refused.
- **`configs/default.yaml`:** `ai.iforest`, `ai_mode: shift`, `ai_shift: 1.0`. There are no `configs/live*.yaml` files. `render.yaml` and `deploy/start.sh` name no detector, and the Docker build uses `default.yaml`, so they need no change. The `Settings.detectors` Python default (used by configs that omit `detectors`, for example many test configs) is still the AE with `"fuse"`. The spec asked only for the yaml, and changing the Python default would change those configs' hashes.
- **Golden test:** `tests/detection/test_sell_side_off.py` read `default.yaml`. It now loads the pre-change values explicitly (`PRE_LIVE_AI`). Every digest is unchanged, including the old default config hash, which also proves the hash safety.
- **UI / health.** `/api/health` now carries `agreement_p` and `agreement_p_ai`. The ai threshold comes from the running Chief (`Chief.ai_agreement_p`), or from the config when no pipeline is running. The alert detail ticks an ai detector only when its p is below its own (shifted) threshold. Before, the UI used a fixed 0.01 for every layer, which under `shift` would disagree with the Chief's `agreement`. The detail also names the detector "ชั้น AI (IsolationForest)" in a non-copy table `DETECTOR_LABEL`. It sits only in the technical details, next to the detector ids, so the plain-view English guard does not apply to it. The lanes, explainer and Telegram read `alert.agreement` or raw p-values, so they needed no change. The auditor has no AE-specific check. The AE wording on the eval page (`app.js`, `eval/report.py`) describes past experiments and is left as is. After review: under `ai_mode: exclude`, `Chief.ai_agreement_p` is 0.0 (the ai layer is never ticked), and `/api/health` also returns `agreement_layers`, from the Chief (`Chief.agreement_layers`) or from the config. The detail then shows "n/2 ชั้น … (ไม่นับชั้น AI)". The Thai explainer text still says "จาก 3 ชั้น"; only an `exclude` config would make that wrong, and production runs `shift`.
- **Docker / memory.** The build stage now trains `ai.iforest` (sklearn), not the AE: there is no torch training. A subprocess test builds and fits the default detectors with torch blocked. After review, the build stage also skips the `train` group (`--no-group train`; `test_dockerfile_two_stages` was updated). An AE config can still be trained locally, because `uv sync` installs that group by default. The runtime was already torch-free and already imported sklearn (the detector registry imports `idsai.ai.baselines`). The model is about 2.3 MB pickled (200 trees). Scoring 34,560 rows × 60 features peaks at about 10 MB of traced allocation, less than the input matrix itself. Training uses the 60 s grid-thinned frame. So no memory concern for 512 MB.
- **Latency, fixed (follow-up from the coordinator):** `idsai.ai.baselines.ForestScorer` re-implements sklearn's `score_samples` in NumPy. It walks all 200 trees at once, `max_depth` steps over padded per-tree arrays, in chunks of 2048 rows. It reproduces sklearn step by step: float32 input, `x <= threshold`, NaN goes to `missing_go_to_left`, the estimator's feature subset (only when `max_features < n_features`, as in sklearn), the per-leaf `depth + c(n_leaf) - 1`, summed in estimator order (a cumulative sum, the same order as sklearn's `depths +=`), then `2 ** (-depth / (T * c(psi)))`, with the single-sample case handled. Both `baseline.iforest` and `ai.iforest` use it for batch and stream scoring. On synthetic data its scores equal `-score_samples` exactly (max abs difference 0.0) for full features, a feature subset, an int `max_features`, the ±Z_CAP edges, NaN, and 1- and 2-row training sets. So eval scores do not change. The scorer is rebuilt from the model at fit and load and is not stored, so the state and its sha are unchanged. Measured in one run (one thread, shared CPU, 60 features): sklearn `score_samples` 9.1 ms/row (24 ms in an earlier run under heavier load), the NumPy scorer 0.13 ms/row, and `detector.score` on a 1-row polars frame 1.2 ms. Of that 1.2 ms, about 1.0 ms is `feature_matrix` (polars to numpy), which every feature detector already pays.
- **Eval tests:** `tests/eval/test_experiments_smoke.py` built its config from `default.yaml` and expected the AE detector set. It now loads `configs/eval_prev_live.yaml`, the config the real evals use, with the same overrides. No eval code changed. Two other test edits follow from the new default: the default-detector assertion in `tests/test_config.py`, and `FakePipe.chief.ai_agreement_p` in `tests/product/test_api.py`.
- **Full suite** (default selection, `-m 'not network'`): 1625 passed, 2 skipped, 5 deselected. That is 1622 passed in the full run, plus the 3 eval smoke tests re-run green after the fix. The 5 deselected are the 4 network tests plus `test_windows.py::test_one_symbol_day_under_5s`. That timing test fails (6.2 s against a 5 s limit) because the CPU is shared with the running M2 eval. It measures only `compute_windows`, which this change does not touch, and it also fails on the unchanged code under the same load. `ruff check .` is clean. (`ruff format --check` flags 3 hunks in `tests/test_cli.py`; none of them are in code this change adds.)

## Sell side on in live

`configs/default.yaml` now sets `features: sell_side: true`. This is the M4 sell side (REPORT section 10, M4 rerun on `feat/m2` b219a5c): sell phase labelled 0.551, SEMI-SYN bear-raid recall 0.172 -> 0.544 (0.465 named correctly), pump recall 0.739 -> 0.748, FA 1.650 -> 1.556, hard FA 11.17 -> 9.76.

- **Stream = batch.** No pipeline code had to change. `BarBuilder` builds `sell_rush_orders` from live, archive and replay trades. Gap and empty bars carry 0. `StreamingWindows` passes `low` and `sell_rush_orders` into the shared `Kernel`, so `sell_rush_*`, `drop_*`, their `z_` columns and `cusum_sell` come from the same code in batch and stream. `rule_signatures` adds `configs/signatures_sell.yaml` (dump 100104, bear raid 100601 rev 2) whenever the flag is on, so `serve`, `train --profile live`, `demo-pack` and `load_bundle` all build the same rule set. The stream parity tests in `tests/pipeline/test_stream.py` and `tests/detection/test_streaming_parity.py` build their config from `default.yaml`, so they now run with the flag on. Scored rows, F, lanes and the final alerts are exactly equal to batch, `phase` included. A new test checks that the sell columns and the sids 100104 and 100601 are present. Another checks that a flag-off pipeline still drops `sell_rush_orders` from the bus.
- **Phase in the product.** `Alert.phase` was already stored (in the alert JSON), returned by `/api/alerts`, `/api/alerts/{id}` and the WebSocket, shown as a badge on the alert card and detail, and added to the explainer text ("ช่วง: กำลังพุ่ง" / "ช่วง: กำลังเทขาย"). Telegram uses that explainer text. MM-T006 reads "ทุบราคา" from the taxonomy. One fix: Telegram's `HISTORY_TH` is a statistic measured on the rise of real pumps, so a sell-phase alert is now sent without it. The wording stays neutral: a statistical anomaly, no accusation, no advice, and `p` is called a rarity, never a probability. New API and Telegram tests cover MM-T006 with `phase="sell"`.
- **Model inputs are unchanged.** `model_features` excludes the sell columns, so `ai.iforest` sees the same 60 features. The extra columns go only to the rules and the explainer.
- **Memory (Render 512 MB).** Feature columns go from 76 to 93 (+17: 8 raw, 8 z, `cusum_sell`). At runtime the kernel's baseline keeps 1440 samples × 8 more float64 per symbol (about 92 KB, at most about 0.2 MB with buffer growth). The prefix sums add a little more. Summed over 4 symbols that is under 1 MB, and each scored row grows by 17 floats. Training (Docker build stage, not the 512 MB runtime) holds about 1.2 MB more per symbol-day of windows, under about 40 MB for the live bundle. These figures are estimates from the shapes, not measured on Render.

The flag is dumped only when on, so pre-M4 goldens keep their hashes once they set `sell_side: false` explicitly (`tests/detection/test_sell_side_off.py`, `tests/test_config.py`, `tests/detection/test_sell_rules.py`).
